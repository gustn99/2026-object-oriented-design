## 불필요한 세부 구현을 캡슐화하여 결합도 낮추기

> **35p**
> 좋은 설계란 오늘 요구하는 기능을 온전히 수행하면서 내일의 변경을 매끄럽게 수용할 수 있는 설계다.

객체지향이 말하는 좋은 설계는 결국 변경을 유연하게 받아들이는 설계입니다.
그리고 그 유연함은 협력하는 객체 사이의 의존성을 적절하게 관리하는 데서 나옵니다.

인상 깊었던 건 그 관리의 출발점이 객체를 자율적인 존재로 바라보는 관점이었습니다.
자율적인 객체란 자신의 데이터를 스스로 처리하는 객체입니다.

자율적인 객체를 만들기 위해 캡슐화를 활용한 부분도 인상적이었는데요.
상태와 그 상태를 다루는 로직이 한곳에 캡슐화되어 있어서,
외부는 무엇을 요청할지만 알고 그것이 어떻게 처리되는지는 모릅니다.

<br/>

처음에는 '자율성이 높다 = 결합도가 낮다'로 단순하게 이해했는데요.
둘은 반비례 관계가 아니었습니다.

티켓 판매 예제에서 `TicketOffice`가 스스로 티켓을 팔게 만들면 자율성은 올라가지만,
그러려면 `Audience`를 알아야 하므로 없던 의존성이 새로 생겨 결합도가 상승합니다.
책이 "설계는 트레이드오프의 산물"이라고 말하는 지점입니다.

<br/>

그래서 결합도를 두 층으로 나누어 보게 됐습니다.

- 누구를 아는가 - 협력하는 이상 필연적이고, 자율성을 높이면 오히려 늘어나기도 합니다.
- 내부 구현이 어떻게 돌아가는지 아는가 - 캡슐화가 줄이는 건 이쪽입니다.

그래서 제가 얻은 관점은 이렇습니다.

협력이 기본인 이상 의존성 자체는 필연적이라 없앨 수 없다.
관리해야 할 것은 얼마나 많이 의존하는가가 아니라 내부를 얼마나 아는가입니다.

정리하면 다음과 같습니다.
외부에서 객체의 내부 구현을 모를수록 구현에 대한 결합은 낮아지고 그 객체는 자율적이 된다.
다만 '누구를 아는가'라는 결합은 그대로 남는다.

<br/>
<br/>

아직 프론트엔드에 어떻게 접목할지는 어렵지만,
훅으로 옮겨보면 이런 모양이 아닐까 싶습니다.

```tsx
// 자율적이지 않다 - 도메인 규칙이 컴포넌트로 새어나옴
const { items, setItems } = useCart();

if (items.length >= 10) return;
setItems([...items, item]);
```

```tsx
// 자율적이다 - 훅이 내부 규칙을 스스로 관리한다
const { add } = useCart();

add(item);
```

아래에서도 컴포넌트는 여전히 `useCart`에 의존합니다.
사라진 건 의존 자체가 아니라 내부 규칙에 대한 의존입니다.
반대로 훅이 `items`를 통째로 노출하는 순간, 그 훅은 자율성을 잃습니다.

(아직 읽어보지 않았지만) 
앞으로의 내용은 이 의존성을 어떻게 관리할 것인가로 이어지지 않을까 싶습니다.

익숙한 코드를 새로운 관점에서 볼 수 있어 좋았습니다.
